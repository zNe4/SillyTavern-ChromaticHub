## 1. Scope, authority, and support boundary

- ChromaticHub is **card-scoped**, not a cross-card person database. The durable reference is `(authenticated SillyTavern user, installedCardId, identityId)`. The installedCardId is a random server-issued UUID v4 identifying a **sidecar association**, not an immutable host-provided proof of PNG identity. The opaque per-character UUID remains card-local.
- The **only authoritative identity store** is the companion server plugin's private per-user sidecar. Existing `data.extensions.chromaticHub` in the PNG is *legacy input for a future explicit migration only*; it is never a fallback, mirror, or source for automatic creation/recovery.
- A browser UI extension may call the authenticated plugin API. It cannot directly write the server filesystem. Native SillyTavern editor autosaves do not write sidecar state.
- **Option A accepted:** on ordinary restart, if exactly one valid sidecar binding names an existing exact PNG filename in the same user account, resume it without a confirmation prompt. A wholly invisible deletion and replacement under the same filename can fool this match; V1 expressly does not detect it.
- One local Node/SillyTavern server process exclusively owns the writable data root. External concurrent writers, network-share multi-process configurations, malicious local processes swapping paths, and modified SillyTavern core are **outside supported V1 guarantees**. The implementation must still reject detected malformed paths and symlinks; do not claim race-free filesystem behavior against a privileged adversary.
- Browser installation requires the enabled companion plugin. If unavailable, wrong version, or inaccessible: **no PNG/settings/browser fallback** and no mutating UI route. Display a clear read-only/unavailable notice.
- **Explicitly out of scope:** chat-local NPC writes; group mutations; cross-card global identity linking; image asset movement; automatic PNG-metadata migration; standard PNG/JSON export portability; bundles (future); background watchers; automatic destructive orphan cleanup; changes to legacy deny-only adapter; native ST source patches.

## 2. Storage location and namespace

Derived solely from the authenticated request's trusted `request.user.directories.root`, not from a request body:

```text
<request.user.directories.root>/
  chromaticHub/
    cards/
      <installedCardId>/
        state.json
```

The server also takes the authenticated user's **character directory** from `request.user.directories.characters` for exact PNG existence checks. Folder names use canonical lowercase RFC 4122 UUID v4 `[0-9a-f]{8}-...-4...-[89ab]...`, generated by Node cryptographic randomness; do not include filenames or names in folder paths. Reserve `backups/` for a later separate design; **do not create it as a normal read or write side effect**. Store no registry in a served static directory, Git checkout, `user/files`, or global settings.

No shared mutable `index.json` in V1. Build a derived lookup by scanning **validated** `cards/<uuid>/state.json` records; maintain it under server process synchronization and invalidate/rebuild when needed. If two valid records claim one filename, both are `CONFLICT` and mutations fail. Invalid/corrupt records must not be silently skipped to enable a conflicting attachment; treat ambiguity or incomplete inventory as fail-closed.

## 3. Exact V1 serialized record

Strict JSON object with **exactly five root keys** (no unknown fields):

```json
{
  "storageSchemaVersion": 1,
  "installedCardId": "f996e7c9-3758-4ee8-9bc2-35c349a019a0",
  "stateRevision": 0,
  "binding": {
    "avatar": "Narrator.png",
    "status": "BOUND"
  },
  "registry": null
}
```

**Root fields:**
- `storageSchemaVersion`: integer exactly `1`; unknown integer versions report `UNSUPPORTED_STORAGE_VERSION`, never coerce or reset.
- `installedCardId`: canonical UUID v4, **identical to its parent directory name**; unique per authenticated user's sidecar inventory. Generated by the server at attach, never taken from the caller.
- `stateRevision`: nonnegative safe integer, starting at **0** when attached; increases by exactly 1 on **each successfully committed actual change** of `registry` or persisted `binding`. Overflow refuses a write. This is the **record-wide CAS generation** and is checked *inside* the server-side critical section.
- `binding`: strict object with exactly `avatar` and `status`. `avatar` is the **current recorded PNG filename**, *not* the permanent primary key. `status` is persisted `BOUND | UNRESOLVED | ORPHANED`; `CONFLICT` and `CORRUPT` are **derived read statuses**, never serialized as if they were valid ownership.
- `registry`: **`null` means explicitly attached but UNINITIALIZED**. Otherwise a full `{schemaVersion:1,revision:n,characters:[...]}` validated by the existing `parseRegistry`/identity contract, with no extra keys. Do not pass `null` directly to the old `parseRegistry` (it treats null as invalid); map this **envelope sentinel** to `parseRegistry(undefined)` for the virtual empty revision-0 snapshot on reads/mutation planning. This is not a second way to represent a corrupt registry.

**Registry compatibility:** existing `src/identity-registry.mjs` validates v1 root keys, 128 records maximum, 16 aliases per record, UUID v4, name/descriptor length limits and a 256 KiB serialized registry limit. `planMutation` increments `registry.revision` on actual add/update/remove, except an unchanged update is a no-op. This contract **reuses that exact behavior**. The **first successful add** to `registry:null` writes a materialized registry at revision 1. Do not materialize a registry just for reads or attachment. An explicit valid `{schemaVersion:1,revision:0,characters:[]}` is *materialized*, not the same thing as `null`.

**Limits (V1 draft, to review with filesystem implementation):** raw UTF-8 `state.json` at most **512 KiB**; registry serialized bound **256 KiB** (already implemented); `avatar` at most **255 UTF-8 bytes**, nonempty stem and literal `.png` suffix, no `/`, `\\`, NUL or control characters, no `.`/`..` stem, no leading or trailing whitespace. Exact case-sensitive basename matching. Any exceptional SillyTavern filename outside this scope produces `INVALID_AVATAR` rather than silent sanitization or guessing. File content must be strict JSON (not BOM, comments or JSON5), no duplicate object keys (reject at input decode), prototype-pollution property names, or unexpected fields. Ensure state record size and nested structure depth are bounded; do not silently strip unrecognized fields.

**Serialization:** deterministic documented field ordering/canonical JSON for the full state, UTF-8 encoded, one source of truth; decoding canonicality need not depend on whitespace ordering, but post-write readback must compare validated *semantic* content and `stateRevision` to exactly the intended result. Unknown versions remain readable only as controlled errors; no migration by rewriting them.

## 4. Persisted vs derived effective status

**Persisted state:** `BOUND` (normal), `UNRESOLVED` (known mismatch requiring user action), `ORPHANED` (confirmed delete / user-managed detachment). Any change to persisted status is an **explicit versioned server write**, not an opportunistic side effect of read.

**Read-time effective status**, derived from validated state, current authenticated user's PNG directory and validated inventory:
- `BOUND`: persisted `BOUND`, exact filename exists as an ordinary PNG, and exactly one sidecar claims it. Restart resumes this state without prompts.
- `ORPHANED`: PNG missing, or persisted `ORPHANED`. Preserve the sidecar; do not write on read. If absence is merely *observed* in a read (not explicitly recorded as a delete) and the same filename later reappears, Option A may resume binding, an accepted limitation.
- `UNRESOLVED`: persisted `UNRESOLVED` or an independently observed known mismatch not classed as an orphan.
- `CONFLICT`: two or more records claim a basename, or lookup is not trustworthy because of duplicated/ambiguous ownership. Refuse writes on any affected record.
- `CORRUPT`: malformed record, mismatched directory UUID, unsafe filesystem entry, incompatible storage version (report specific error), or untrustworthy inventory. **Never reset to empty**.

Priority of refusal: `CORRUPT/UNSUPPORTED_STORAGE_VERSION`, then `CONFLICT`, then persisted `UNRESOLVED`, then `ORPHANED`, then `BOUND`. A sidecar that has an explicit persisted `ORPHANED` or `UNRESOLVED` never automatically becomes bound simply because a matching filename reappears: only explicit user recovery may change it.

**Unattached** is not `UNINITIALIZED`: `UNATTACHED` means no sidecar exists for a valid chosen PNG. `UNINITIALIZED` means a sidecar exists but `registry:null`. Pure reads never create either resource.

## 5. Plugin transport: exact V1 request/response envelope

Base path `/api/plugins/chromatic-hub/v1` (subject to pinned plugin ID validation; plugin module ID `chromatic-hub`). POSTs use same-origin credentials, existing ST CSRF header, `Content-Type: application/json`, no CORS wildcard. All request JSON bodies are strict **exact-key** bounded objects; reject extra/unrecognized properties. The plugin must not expose arbitrary filesystem paths or accept client-supplied account IDs, user roots, raw JSON disk records, full replacement registries, user-selected UUIDs, or custom host commands.

**Common response:**

```ts
type HubResult<T> =
  | { ok: true; value: T }
  | { ok: false; code: HubErrorCode; message: string; recoverable: boolean };
```

All writes have a **single authoritative server handler**; success means committed and independently verified on disk. On uncertainty the handler must not report success. Do not return raw card names/aliases in errors, logs, or stack traces.

A successful attached/read snapshot:

```json
{
  "installedCardId": "f996e7c9-3758-4ee8-9bc2-35c349a019a0",
  "stateRevision": 0,
  "binding": {"avatar":"Narrator.png","status":"BOUND"},
  "effectiveStatus": "BOUND",
  "registryStatus": "UNINITIALIZED",
  "registry": {"schemaVersion":1,"revision":0,"characters":[]}
}
```

The `registry` shown here is virtual and cannot be persisted until an explicit mutation. A materialized registry instead yields `registryStatus:"VALID"`. Client never infers server write safety from a UI editor flag.

**API routes** (all scoped by authenticated `request.user`):

| Method/path | Exact request JSON | Success `value` and invariants |
|---|---|---|
| `GET /capabilities` | no body | `{apiVersion:1,storageSchemaVersion:1,writeSupported:true}`; a missing/disabled plugin has no valid capability response. |
| `POST /resolve` | `{avatar}` | If exact PNG exists and has no sidecar, `{attached:false,avatar}`. Otherwise `{attached:true,snapshot}`. Never creates a folder; two claims produce `BINDING_CONFLICT`. |
| `POST /read` | `{installedCardId}` | `snapshot` with effective and registry statuses, or controlled error; no mutation even when PNG missing. |
| `POST /attach` | `{avatar,expectedUnbound:true}` | New record with `stateRevision:0`, `binding.status:BOUND`, `registry:null`. Server generates UUID and atomically creates unique record; two concurrent attaches of same PNG -> one succeeds, other `ALREADY_ATTACHED`. |
| `POST /mutate` | `{installedCardId,expectedStateRevision,expectedAvatar,command}` | Runs existing add/update/remove `planMutation` on current server-held registry. Validates exact bound avatar and effective `BOUND`, checks revision **under lock**, commits only actual changes; success returns full verified `snapshot` and `changed:boolean`. A no-op returns `changed:false` and both revisions unchanged. |
| `POST /rename` | `{installedCardId,expectedStateRevision,oldAvatar,newAvatar}` | A browser-observed successful native rename is an advisory input. Require old avatar equal persisted binding, old PNG absent, new exact PNG exists, and destination unclaimed; commit only a binding rename, bump `stateRevision`, leave registry revision unchanged. If ambiguous, `BINDING_UNRESOLVED`; no guessed recovery. |
| `POST /orphan` | `{installedCardId,expectedStateRevision,expectedAvatar}` | Intended for observed native delete; require recorded matching avatar **absent** and no binding conflict. Set persisted `ORPHANED`, bump state revision once, preserve data. |
| `POST /recover` | `{installedCardId,expectedStateRevision,newAvatar,confirm:true}` | **Explicit user action only.** Require user selection of exact existing unclaimed PNG, old record `ORPHANED` or `UNRESOLVED`, strict revision and conflict check; commit binding as `BOUND`, preserve registry, bump `stateRevision`. Never auto-recover from a name/fingerprint similarity. |

A `/rename` hint arriving after another tab already reconciled a rename with a new revision yields `REVISION_CONFLICT`; never overwrite based solely on an event. On a missed rename, an old missing avatar is reported orphaned; the user can explicitly `/recover` after an appropriate persisted transition. `/recover` is not a background operation.

**Known plugin security:** the pinned ST server applies its session/user and CSRF middleware before loading server plugins, but the plugin must still check the authenticated request user and never assume its routes are available anonymously. The initial module must not weaken CSRF, login or host sandbox settings.

## 6. Failure codes and HTTP mapping

| Code | HTTP | Behavior |
|---|---:|---|
| `INVALID_REQUEST`, `INVALID_AVATAR`, `INVALID_UUID`, `INVALID_COMMAND` | 400 | No write; request rejected. |
| `UNAUTHENTICATED`/`FORBIDDEN` | 401/403 | Do not reveal whether another user's record exists. |
| `CARD_NOT_FOUND`, `STATE_NOT_FOUND` | 404 | No write or implicit new attachment. |
| `ALREADY_ATTACHED`, `REVISION_CONFLICT`, `BINDING_CONFLICT`, `BINDING_UNRESOLVED`, `ORPHANED` | 409 | No write; the UI refreshes state or offers explicit recovery. |
| `INVALID_SCHEMA`, `UNSUPPORTED_STORAGE_VERSION`, `UNSUPPORTED_REGISTRY_VERSION` | 422 | No write, no reset; report controlled recovery. |
| `REGISTRY_LIMIT_EXCEEDED`, `STATE_LIMIT_EXCEEDED` | 413 | No write. |
| `STATE_REVISION_OVERFLOW`, `REGISTRY_REVISION_OVERFLOW` | 409 | No write; requires explicitly designed migration. |
| `READ_FAILED`, `WRITE_REJECTED` | 500 | Failed before confirmed commit; no retry without checking state. |
| `WRITE_UNCERTAIN`, `READBACK_MISMATCH` | 503 | Possibly committed; **quarantine affected record**; no automatic replay, and verify independently before any further write. |
| `UNSUPPORTED_CONTEXT`, `PLUGIN_VERSION_MISMATCH` | 409 | Unsupported operation or client/server mismatch; no PNG fallback. |

**Error discipline:** all codes are controlled, fixed text without exposing card/character names or filesystem details. Use `recoverable:true` only when the recommended action is an explicit refresh/re-read or user repair. Unknown or unsupported fields fail closed; no silent coercion. Existing pure `planMutation` result codes (e.g. `IDENTITY_NOT_FOUND`, `CARD_CAPACITY_EXCEEDED`, `BYTE_LIMIT_EXCEEDED`) should be preserved via a documented server-to-client mapping rather than collapsed to generic 500s.

## 7. Serialization, isolation, and crash behavior

**Serialization domain:** V1 takes a **per-authenticated-user mutation lock** for attach, rename, orphan, recover, and registry mutation. Simpler and safer than separate per-card locks plus a second global filename index lock; small V1 cardinality makes this acceptable. Exactly one server-process queue per user; two browser tabs using the same user compete through it. Reading / resolving the entire user inventory for a write, checking uniqueness, validating owner PNG, comparing `expectedStateRevision` and committing must happen inside that critical section.

**Attach:** write to a newly created UUID directory in the user's private `chromaticHub/cards`, using exclusive creation; check avatar uniqueness and no conflicting unreadable records before commit. If the operation fails pre-commit, clean only its own newly allocated temp artifacts when safely identifiable. Never delete a card or another sidecar in rollback. If an attach may have committed, refuse retry and require resolve/read to determine outcome.

**Mutation protocol (server-side, bounded):**
1. Authenticated user scope, strict request/body/filename validation. Reject unknown fields or unsafe record shapes.
2. Acquire user's mutation lock. Load/validate the exact record and full current inventory; check `effectiveStatus:BOUND`, matching avatar and `expectedStateRevision`. Validate the target card is still a regular exact PNG inside the user's character directory.
3. Invoke existing trusted pure registry planner on a private snapshot; reject invalid commands/versions. Check that any resulting change is real. For no-op: return the existing verified snapshot with `changed:false`, no write.
4. For a real change, generate next registry and `stateRevision+1` (both bounded). Serialize a whole new record. **Never mutate the native PNG**.
5. Use a verified private temp file in the **same directory**, exclusive create, restrictive permissions; write/flush, verify complete bytes, atomic rename to `state.json` and flush the parent directory where supported. Apply a carefully reviewed POSIX-local fsync policy. Handle directory/rename/fsync failure without asserting durable success.
6. Independently re-open and validate `state.json`, exact new revision/content and owner binding; only then return `ok:true`. If an error arises after any possible publication/rename, report `WRITE_UNCERTAIN` (even if the new file seems present but crash durability is unproven), quarantine the record, and stop further automatic mutation until explicit inspection/reconciliation.
7. Release lock on *every* path. No automatic retry on HTTP timeout, client disconnect, uncertain response, or conflicting state.

**Filesystem threat model:** requests cannot choose paths, user handles, filenames as directory identifiers, or temp names. Guard against relative traversal, unexpected symlink/hard-link targets, absolute paths, changed inode, oversized records, malformed JSON, link-count anomalies, and preexisting temporary artifacts. Use `lstat`, no-follow descriptor flags where supported, exact regular-file checks, and safe directory anchoring; **do not claim** these alone defeat an actively malicious local process that can race path components. The precise Node API and supported filesystem matrix must be verified in D2-C with fault injection before any native activation. Private directory/file mode target `0700` / `0600` where the OS permits it, accounting for umask and per-user process permissions.

**In-process quarantine vs crash restart:** after a potentially published failure, the process keeps the specific owner unavailable for writes. On a later restart, do not quietly discard temp/journal anomalies; validate the complete record and any remaining artifacts. A correct single `state.json` with no ambiguous debris can be inspected and resolved using a separately reviewed recovery step; this contract does not promise automatic replay or rollback across crash. A durable journal is **not** part of this first schema. If D2-C cannot demonstrate bounded safe recovery without one, stop and amend this contract before implementation.

## 8. User/card lifecycle and portability

- **Normal restart:** validate file/index and auto-resolve a unique matching PNG filename to its persisted UUID (Option A), without prompting. A fully invisible same-filename replacement is an accepted blind spot.
- **Native autosave:** no plugin mutation; registry and stateRevision remain unchanged. Browser state refreshed from plugin on next query, never copied from PNG fields.
- **Rename:** new filename is accepted only under the endpoint's explicit preconditions; no other card's claim may be stolen.
- **Duplicate:** SillyTavern's copied PNG is not sidecar-copied. It starts `UNATTACHED` and may be explicitly attached to a fresh empty sidecar. **Copying source registry into it is a separate later user-directed feature**.
- **Delete:** preserve sidecar and allow explicit orphan/recovery; no destructive purge by native delete event.
- **Import/replacement:** detect obvious collision; silent same-name replacement without a detectable signal is an accepted V1 limitation. Never overwrite the old sidecar based on an imported PNG.
- **Legacy metadata:** do not automatically migrate, delete or rewrite `data.extensions.chromaticHub`. Its existence neither creates a sidecar nor overrides an existing one. User-directed migration later must validate and warn of possible stale content.
- **Native PNG/JSON export:** does **not** carry the Hub sidecar. The UI must warn: *“SillyTavern card exports do not include ChromaticHub identities. Back up the ChromaticHub data directory separately.”* Until portable bundles exist, back up the relevant complete **user-scoped `chromaticHub/` directory together with the cards**. A consistent point-in-time backup should be taken with the SillyTavern server stopped; do not claim ordinary ST card export or built-in chat backup is complete.
- **Plugin missing:** UI read-only/unavailable (not fake empty registry), with actionable message about the companion plugin and never a fallback PNG write.

## 10. Explicit design-review decisions

For owner approval, this candidate fixes: (a) per-user private UUID folder; (b) strict five-key state envelope with `registry:null` for attached-but-uninitialized; (c) `stateRevision:0` on attach, versioned whole-record CAS, no-op does not bump; (d) user-wide server mutex for V1; (e) Option A unique-filename restart reconnection, with recorded known blind spot; (f) explicit attach and explicit recovery; (g) no bundle export/import or PNG fallback in initial writable release; (h) uncertainties quarantine and no automatic retry.

**Still implementation-gated:** the exact Node descriptor-based filesystem operations and error-proof durability evidence, request-body DoS behavior of SillyTavern's upstream parser, native integration tests, UI/extension wiring, and all real installations. If these fail the concrete environment capability tests, amend this contract before writing to any installed user's data.
